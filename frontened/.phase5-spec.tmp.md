21	## 2. Backend facts you must respect
22	POST /resumes/upload (multipart field `file`; login optional) -> 200 {saved: boolean, resume_id: number | null, parsed: {skills: string[], target_role: string | null, role_source: "headline" | "inferred_from_skills" | "unknown", experience_level: "student" | "fresh_grad" | "junior" | "mid" | "senior", projects: string[]}, needs_manual_role_input: boolean}.
23	Guests: nothing is stored (`saved` false, `resume_id` null). Logged-in users: stored, `saved` true.
24	Errors (all `{detail: string}`): 413 "File too large. Max 5 MB."; 400 "Unsupported file type '.xyz'. Only PDF and DOCX are allowed."; 422 "No readable text found in the file. It may be a scanned/image-based document." or "Resume parsing failed - could not understand document structure." or "Failed to extract text: ..." or "Failed to download file: ..."; 502 upload/storage failure. Parsing can take up to ~90 s.
25	IMPORTANT behaviours of the backend that the UI must reflect:
26	- Live interviews use only the FIRST 4 skills of the list (order matters); the Question Bank uses all of them.
27	- `getContextPayload()` in the store sends `resume_id` when the skills are untouched, and `skills` (+ `target_role`) once `skillsEdited` is true. Therefore the skills list must be committed to the store only if it really changed (order-sensitive comparison), otherwise the saved-resume link is needlessly dropped.
28	- The backend ignores `experience_level` for now. Keep it in the store and the UI, but never send it anywhere.
